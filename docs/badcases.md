# Bad Case 复盘

> 记录纪律：每次评测跑完，把未通过的 case 按失败模式归类记在这里；
> 每类给出根因 → 对策 → 修复后的前后对比。这份文档是消融表之外最有说服力的
> 质量证据（"error analysis 是一切的地基" — Hamel Husain）。
> 例句库（eval/knowledge/examples.jsonl）里的 few-shot 只能从这里的人工修正产生。

## 失败模式分类

| 类别 | 判定特征 | 典型对策 |
|---|---|---|
| A. 选表错误 | table_recall < 1，SQL 用错表 | 表注释补充、检索 top_k 调整、业务字典补条目 |
| B. 口径理解错 | 表选对了但聚合/过滤口径错（如用目录价算成交额） | 业务字典补口径、few-shot 例句 |
| C. 过滤值写错 | empty_result 后修复失败（大小写/中英文/日期格式） | 样例行覆盖该列、repair 提示强化 |
| D. SQL 方言错 | syntax_error / execution_error（SQLite 不支持的语法） | 提示词方言约束、修复提示 |
| E. 幻觉列名/表名 | no_such_column / no_such_table 且修复失败 | schema 上下文排版、few-shot |
| F. 语义歧义 | SQL 合理但与 gold 口径不同（题目本身多解） | 修评测集题面，或标注可接受多解 |
| G. 结果比对误判 | 人工看结果等价但 EX 判错（列序/舍入/单位） | 修 scorer 规则并加回归测试 |

## 记录模板

```

- 问题：
```

### smoke-06 · 类别 F（兼有输出列冗余） · 2026-08-27
- 问题：每个商品品类下各有多少个商品？
- 预测 SQL：`SELECT c.id AS category_id, c.name, COUNT(p.id) FROM categories c LEFT JOIN products p ON p.category_id = c.id GROUP BY c.id, c.name ORDER BY c.id`
- gold SQL：`SELECT c.name, COUNT(*) FROM categories c JOIN products p ON p.category_id = c.id GROUP BY c.name`
- 根因（一句话）：模型多输出了一列 `category_id`（题目没要），且用 LEFT JOIN 把"零商品品类"也计为 0——两处口径都"合理但与题意不符"，EX 按列数直接判负。
- 对策（已实施）：SQL 系统提示词新增"输出列纪律"规则（只 SELECT 题目要求的列）。
  业务集同类失败：biz-0097/0107/0121/0128/0150（"某指标是多少"多带说明列）。
- 复验：prompt-fix 轮重跑后填数。

### smoke-12 · 类别 F · 2026-08-27
- 问题：按销量（销售数量合计）最高的前5个商品是哪些？
- 预测 SQL：加了 `WHERE o.status IN ('completed','shipped')` 后再聚合
- gold SQL：不区分订单状态，直接对 order_items 聚合
- 根因（一句话）：口径分歧——"销量"是否应剔除已取消订单？模型选择了剔除（业务上完全站得住），gold 是全量口径；题目没有指明，两种解释都对。
- 对策（已实施）：**用系统自身机制修**——业务字典新增"销量"口径条目
  （SUM(order_items.quantity)，不区分订单状态），BM25 检索命中后自动注入。
  不改题面，保持评测集稳定。业务集同类失败：biz-0028/0059/0125/0139/0157。
- 复验：prompt-fix 轮重跑后填数。

（结论：首轮 smoke 90%（18/20），两条失败均为 F 类——评测集题面歧义，而非模型能力缺陷。
这正是 error analysis 的价值：第一轮就发现"该修的是题目，不是模型"。）

**对比轮总结（2026-08-27）**：baseline 93.3% → prompt-fix 97.8%（同模型 gpt-5.5、
同评测集、同 3 重复）。按题配对：平均 +4.44pt，95% CI [+1.72, +7.17]；23 题变好、
7 题变差，符号检验 p=0.0052。

> **口径修正（2026-09-23）**：本段最初写的是"按题多数票配对翻转 5:0，McNemar p=0.0625，
> 不显著"，区间为 [90.8, 95.2] / [96.1, 98.8]。复查发现两处问题：① 区间把 3 次重复
> 计为 495 个独立样本，而同题重复高度相关（设计效应 1.52），区间偏窄；② 多数票把每题
> 3 次结果压成一个对错，丢掉了"3 次中对 2 次→对 3 次"这类改进，也掩盖了 7 题的部分退步
> （"零回归"不成立）。现改为按题聚类校正区间（[90.1, 95.6] → [95.5, 98.9]）与按题配对比较，
> 均可用 `make report` 从 eval/results/ 下的原始 JSON 复算。
残留失败：B3 排序并列 1 例（评测器已知问题）+ 成交金额类偶发变体 4-5 例。

**held-out 终考（2026-08-27）**：71 题密封集（全程未参与调优）三轮 208/213 =
**97.7% [92.3, 99.3]**（聚类校正后；原写 [94.6, 99.0]），与 dev 的 97.8% 一致。

> **口径修正（2026-09-23）**：原文结论"提升可泛化、无过拟合"过强。业务集由模板参数展开后
> 按题随机切分，71 题中 69 题的 SQL 结构在 dev 里出现过，所以 holdout 只说明结果不依赖
> 具体参数取值，不能说明对新题型的泛化。按 SQL 结构切分的 holdout 尚未构建。
3 个失败均为已知模式：biz-0174 为 LIMIT 切在并列销量中间（scorer 并列容忍的
已知局限：第 5/6 名同为 228，两种取法都对，属评测集非唯一解缺陷）；
biz-0211 单轮 LLM 调用失败；biz-0222 单轮生成方差。无新失败模式。

## 业务集 baseline 复盘（2026-08-27 · EX 93.3%，462/495，模型 gpt-5.5）

25 个未通过 case（多数 67% = 三轮错一轮的生成方差），把失败 SQL 在演示库上
逐条执行验证后归为三类：

### B1 · 状态过滤口径（B 类，最大头，约 15 case）
- 表现：模型自行给统计加 `o.status IN ('completed','shipped')`。已数值验证：
  biz-0009 pred 126934.03 vs gold 165417.66——差值正是被剔除的订单。
- 波及：成交金额类（0009/0031/0040/0092/0129/0135/0150/0162/0165）、
  销量类（0028/0059/0139/0157）、部分支付/订单计数题的偶发变体。
- 根因：模型的业务直觉（"取消的不该算"）与库口径（全量）冲突，题面未指明。
- 对策（已实施）：业务字典"成交金额/GMV/销量"三条口径注明"不区分订单状态"；
  SQL 提示词新增规则"不要自行添加题目未提出的过滤条件（尤其订单状态）"。
- 复验（prompt-fix 轮）：**该类全部稳定失败案例转绿**（0028/0059/0139/0157 等
  三轮全过），整体 EX 93.3%→97.8%；残留 4-5 例 67% 偶发变体（0010/0053/0061/
  0070/0141/0145/0158 中的成交金额题，单轮偶发状态过滤）。

### B2 · 输出列冗余（模型输出纪律，约 6 case）
- 表现：问"某指标是多少"时附带品类名/城市名/月份列，甚至字面量列
  （biz-0150：`SELECT '图书文娱', '2025-03', SUM(...)`）；列数不一致直接判负。
- 波及：0097/0107/0121/0128/0150/0068（中文别名列等价、无害变体）。
- 对策（已实施）：提示词"输出列纪律"规则。
- 复验（prompt-fix 轮）：**列数不一致类失败清零**（0097/0107/0121/0150 三轮全过）。

### B3 · 排序并列（G 类，评测基建已知问题，1 case 稳定复现）
- 表现：biz-0125 前 10 商品，两组并列销量（228/228、227/227），pred 加了
  `p.id` 决胜、gold 未加——**行集完全相同，仅并列内顺序不同**，被判负。
- 对策（已实施，刻意排在对比轮之后以保证两轮用同一把尺子）：scorer 增加
  并列容忍——把 gold 的 ORDER BY 解析为输出列，两侧按排序键切连续分组、
  组内多重集合比较；解析不到排序键保持严格。4 个回归测试。
- 复验：biz-0125 的原始 pred/gold 在新 scorer 下 match=True；
  历史报告数字保持原样引用（当时的尺子），后续跑批自动受益。

（注：biz-0020/0084/0143 等 67% 且末轮 SQL 与 gold 等价的 case，为失败轮
生成了 B1/B2 型变体所致——根因同上，不单列。）

## BIRD baseline（2026-08-28 · EX 61.3%，92/150，单轮，模型 gpt-5.5）

150 题固定子集（seed=42 抽自 1534 题全量 dev），选表召回率 95.5%。
（该数字是 150 题子集、gpt-5.5、单次运行，不能与论文或排行榜上的全量结果直接比较。）失败 58 题分布：结果多重集
不一致 ~34、行序/内容不一致 ~13、列数不一致 ~11——多为真实语义难题
（跨多表推理、evidence 理解、复杂比例计算），与业务集的口径/纪律类失败
性质不同，属模型能力边界。逐题归因与 RAG 消融（SCHEMA_RAG=off 对照）
留作后续迭代方向。

跑批过程战果：第一次尝试在第 28 题被模型生成的未闭合反引号 SQL 砸停，
暴露守卫只捕 ParseError 不捕 TokenError 的缺陷——已修复（SqlglotError
全族捕获 + 回归测试）。真实基准逼出真实 bug，这就是跑公开基准的意义。


**RAG 消融（2026-08-28，同 150 题、同模型、各单轮）**：全量 schema 直供
**64.7% [56.7, 71.9]** vs 检索选表 **61.3% [53.3, 68.8]**。按题配对：直供 − 检索
= +3.33pt，95% CI [−2.05, +8.71]，11 题直供对而检索错、6 题相反，符号检验 p=0.33——
**两者无法区分**。成本上检索仅节省约 3% token（98.6 万 vs 101.9 万），而 95.5% 的选表
召回率意味着约 4.5% 的题目在检索阶段就缺表。

结论：在上下文装得下的规模上，检索没有可测的收益，却多一个失败点。据此把
SCHEMA_RAG=auto 的启用判据从"表数 > top_k"改为"全量 schema 字符数 >
SCHEMA_RAG_AUTO_MAX_CHARS（默认 16000）"，并留回归测试。

> **口径修正（2026-09-23）**：原文写的是"检索只亏不赚"。配对区间含 0，准确率上并不能说
> 检索更差；这个设计决定的依据是"准确率无可测差异 + 成本收益可忽略 + 多一个失败点"。
